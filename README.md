# Router State Forgery

## Proposal

This document proposes a new attack scenario: Router State Forgery (RSF).

## Definition

Router State Forgery is the manipulation of attacker-controlled framework routing, hydration, or component-state metadata to induce a server-side framework runtime to materialize application state that would otherwise remain undiscovered through normal client navigation.

RSF is not tied to a specific framework implementation. Instead, it describes a class of attacks where frameworks expose internal state-resolution mechanisms through client-controlled protocol inputs.

## Core Idea

Modern web frameworks maintain complex state representations to support:

- client-side navigation
- server-side rendering
- hydration
- partial rendering
- component streaming
- incremental data loading

These representations are normally generated by framework-controlled client code.

However, if the server-side runtime accepts these representations as valid without independently verifying their integrity, an attacker may forge framework state and cause the server to resolve a different application state.

## Security Boundary

The vulnerable assumption:

> Framework-generated client state is trustworthy because it was generated by the framework.

The correct assumption:

> All client-provided framework state is attacker-controlled input.

Framework state should only influence rendering behavior, not:

- authorization decisions
- access control
- exposure of sensitive data
- privileged server-side actions

## Attack Model

An RSF attack generally follows:

1. Identify a framework-specific state representation.
2. Determine how the server consumes this state.
3. Modify or forge the state representation.
4. Trigger server-side resolution.
5. Observe newly materialized application state.

Conceptually:

```
Client-controlled state
|
v
Framework state resolver
|
v
Server-side component/data resolution
|
v
Serialized application state
```

- Is router state authenticated or validated?
- Can forged state reference undiscovered routes/components?

- Can this expose:
  - component metadata
  - internal identifiers
  - secrets
  - PII
  - privileged props
  - dependency information?

## RSF vs Existing Concepts

RSF is not:

- simple route enumeration
- forced browsing
- IDOR/BOLA
- source-map exposure
- static JavaScript disclosure

The key distinction:

The attacker is not simply requesting a hidden resource.

The attacker is manipulating the framework's internal representation of application state and causing the framework runtime to resolve that state.

## Impact Levels

### RSF-Discovery

Framework state manipulation reveals previously undiscovered application structure.

Examples:

- hidden components
- dependency graphs
- route metadata

### RSF-Disclosure

Forged state causes sensitive data to be serialized.

Examples:

- PII
- secrets
- internal backend state

### RSF-Authorization

Application incorrectly uses framework state as authorization context.

Examples:

- assuming a router state means a user reached a privileged workflow
- exposing privileged data based on forged component state
