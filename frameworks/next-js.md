# Next.js

## Overview

Next.js App Router provides a concrete implementation to investigate within the Router State Forgery (RSF) research area.

The framework maintains client-side representations of application navigation state that are transmitted to the server during client-side navigation.

The research question is whether attacker-controlled modification of these representations can influence server-side state resolution.

---

## Relevant Mechanisms

### React Server Components (RSC)

Next.js App Router uses React Server Components to stream serialized component trees from the server.

Relevant protocol components:

- RSC requests
- `RSC: 1`
- `Next-Router-State-Tree`
- `text/x-component` responses

---

## Router State Representation

Next.js maintains a router state tree representing the current application navigation state.

Relevant concepts:

- route segments
- nested layouts
- parallel routes
- loading states
- component hierarchy

During client-side navigation, the client sends router state information to allow the server to determine the required application state.

---

## Trust Boundary

The security question:

Does Next.js treat router state as:

1. Client navigation context only

or:

1. Authoritative input for server-side state resolution

RSF investigates cases where attacker-controlled framework state influences server-side materialization.

---

## Research Hypothesis

An attacker may be able to modify framework-generated router state metadata and cause the Next.js runtime to resolve application state that would not normally be materialized through legitimate client navigation.

---

## Investigation

### Attacker-Controlled Inputs

Potential inputs:

- `Next-Router-State-Tree`
- RSC-related headers
- navigation metadata
- route tree structures

---

## Research Questions

- Is router state cryptographically protected?
- Is router state validated against server-side routing information?
- Can arbitrary route segments be introduced?
- Can parallel routes be manipulated?
- Can hidden layouts/components be resolved?
- Can additional component dependencies be exposed?
- Can serialized server state differ from normal navigation?

---

## Experimental Methodology

Compare:

### Legitimate Navigation

Normal browser navigation generated by the framework client.

### Forged Navigation

Manually modified framework requests.

Measure differences in:

- executed server components
- returned RSC payloads
- serialized state
- component references
- dependency references
- sensitive data exposure

---

## Impact Classification

### RSF-1: State Discovery

Framework state manipulation reveals application structure.

Examples:

- hidden routes
- component hierarchy
- dependency information

---

### RSF-2: State Disclosure

Forged state causes sensitive information to be serialized.

Examples:

- server component props
- internal identifiers
- PII
- secrets

---

### RSF-3: Authorization Impact

The application incorrectly relies on framework state as authorization context.

Examples:

- granting access because router state indicates a privileged workflow
- returning privileged data based on forged component state

---

## Mitigation

Applications should:

- treat all framework-generated client metadata as attacker-controlled;
- never use router state as authorization evidence;
- perform authorization checks against server-side identity and resources;
- separate rendering state from security decisions.
